# 抖音多账号入口面板

## Goal

一个 Windows 桌面应用，把用户的 4 个抖音账号变成**4 个一键直达的入口**：每个账号各自保持一份独立、持久的浏览器登录态，点一下就进入该账号的创作者中心，**永远不需要"退出登录 → 切换账号 → 重新扫码"**。

用户原话："说简单点可能我只需要方便登录的 4 个入口。"

## Background（已勘察事实）

- 本仓库为**全新空项目**：除 `.trellis/` 脚手架与 `AGENTS.md` 外无任何代码、无既有约定文档、无历史任务记录。技术选型不受既有代码约束。
- `.trellis/spec/{backend,frontend}/` 全是未填充的占位模板，无可继承的项目约定。
- 运行环境（已实测）：Windows；Node v24.20.0、pnpm 11.7.0、Python 3.11.9 可用；仓库尚未 `git init`。
- 已实测：系统 Chrome `C:\Program Files\Google\Chrome\Application\chrome.exe` v154.0.8037.58；系统 Edge 亦存在。
- 已实测：Electron 44.5.1 可经 npmmirror 镜像安装并解压运行。
- 已实测：**DSH 沙箱 shell 内 Chrome 与 Electron 均无法启动**（crashpad 被拒绝访问 → 自我终止）。仅影响开发期验证，不影响用户双击运行。
- 目标用户：拥有 4 个抖音账号的个人创作者。
- 核心痛点：每次发视频都要在多个抖音账号之间切换登录。

## Key Decisions

- **D1 通道 = 浏览器自动化，而非官方 API**。用独立持久化的浏览器配置目录承载各账号登录态。选择理由：个人号零资质门槛，不依赖开放平台能力审核；登录态持久化由浏览器配置天然提供。
- **D2 第一交付物 = 4 个免登录入口面板**，不做自动发布。用户在多选中勾选过"每账号独立文案 / 数据看板 / 作品管理"，随后明确收缩为"只要方便登录的 4 个入口"；两者工作量差一个数量级，以用户最终表述为准。
- **D3 形态 = Electron 桌面 App**（用户选择）。
- **D4 抖音页面不放进 Electron 窗口**，一律跑在用户系统浏览器里。理由：Electron 内嵌窗口的 UA/内核特征与真实 Chrome 不同，会把"登录态能长期保住"这个核心价值置于风险中。
- **D5 MVP 不做登录态自动检测**。理由见 Out of Scope。

## Requirements

### R1 账号管理

- 支持添加、重命名、删除抖音账号；目标 4 个，但**账号数量不得硬编码**。
- 账号以**用户自定义备注名**标识（如"主号""美食号"）。
- 每个账号拥有独立、互相隔离的登录态存储。
- 列表展示每个账号的备注名、上次打开时间、以及登录数据是否丢失（profile 目录被手工删除时须显式提示，不得静默当作正常账号）。
- 删除账号必须二次确认，并由用户选择「仅移除记录」还是「连登录数据一并删除」。

### R2 登录态持久化

- 首次登录由用户手动完成（扫码）；登录态由浏览器配置目录自动落盘。
- **关闭并重开应用后，登录态仍然有效，无需重新登录**（核心需求）。
- 一个账号的登录态异常，不得影响其他账号。
- 登录态过期时提供短路径恢复：卡片上直接有「打开登录页」入口。

### R3 打开行为

- 点击账号卡片即用该账号**专属的浏览器配置**打开抖音创作者中心。
- 同一账号重复点击不得新开第二个窗口，应复用已有实例。
- 关闭面板后，已打开的浏览器窗口必须继续存活。
- 浏览器缺失或路径异常时，界面须给出可操作的提示（含手动指定路径的能力），不得静默失败。

## Acceptance Criteria

| # | 可观测结果 |
|---|---|
| AC1 | 首次启动显示空状态引导；界面中不存在任何写死的账号数量 |
| AC2 | 添加账号后，磁盘上出现独立的 profile 目录；连续添加 4 个账号得到 4 个**互不相同**的目录 |
| AC3 | 点击账号打开浏览器，落在抖音创作者中心；4 个账号的浏览器可**同时存在、互不干扰**（各自登录不同账号） |
| AC4 | 关闭面板进程后，已打开的浏览器窗口**仍然存活** |
| AC5 | 重开面板，账号列表从磁盘正确恢复，上次打开时间已更新 |
| AC6 | **扫码登录一次后，关闭该浏览器窗口并重开面板、再次点击同一账号 → 免扫码直接进入** ← 本任务的核心验收点 |
| AC7 | 同一账号窗口已开着时再点，不新开窗口，复用已有实例 |
| AC8 | 「彻底删除」账号后，记录与 profile 目录一并消失；「仅移除记录」则保留 profile |
| AC9 | 手工把 `accounts.json` 改成非法 JSON 后启动：应用不崩溃，原文件被备份为 `.corrupt-*`，界面明确告警，用户数据未被静默清空 |
| AC10 | 当只能回退到 Edge 或找不到浏览器时，界面有明确可见的异常提示 |
| AC11 | 从 Windows「设置 → 应用」或应用内入口卸载后，`%LOCALAPPDATA%\DouyinAccountHub\` **整体消失**（运行时与登录数据一并清除），且源码目录 `dy` 毫发无损 |

## Requirements（续）

### R4 安装与卸载

- 运行时位于 `%LOCALAPPDATA%\DouyinAccountHub\runtime\`；账号数据位于 `%LOCALAPPDATA%\DouyinAccountHub\data\`。**源码与项目文件不进入这两个目录**（原因见 `design.md` §2.4）。
- 应用内提供「卸载」入口：二次确认 → 应用退出 → 清理。
- 在 `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\` 注册卸载项，使应用出现在 Windows「设置 → 应用」列表中（`HKCU` 即可，不需要管理员权限）。
- 提供 `uninstall.cmd`，应用无法启动时仍可卸载。
- **用户已确认：卸载 = 彻底清除，`runtime\` 与 `data\` 一并删除**，不保留登录态。代价是重装后需重新扫码，已接受。

## Out of Scope（本轮明确不做）

- **自动发布视频**（选视频 → 填文案 → 提交）。属于下一个任务；本次的账号 → profile → 浏览器的映射是其地基。
- **一稿多发 / 每账号独立文案**。同上。
- **数据看板（粉丝、播放量）与作品管理**。
- **定时发布**。
- **登录态自动检测**。实现它需要解析抖音页面（随改版即失效）或解析 Chrome 的加密 Cookie 库（需 SQLite + DPAPI）。而「显示上次打开时间」+「打开登录页」已覆盖绝大部分价值，代价却低得多。**这是有意识的取舍，不是遗漏。**
- **官方开放平台 API（open.douyin.com）路线**。需开发者应用审核与视频发布能力授权（通常要求企业主体资质），与"个人号可用"目标冲突。
  > 该资质门槛描述来自既有认知；本会话联网检索不可用，未能核实。若后续拿到能力授权，可作为独立任务重新评估。
- **安装包（installer）**。本轮交付 `install.cmd` + `start.cmd` + `uninstall.cmd`；打包成 MSI/EXE 安装向导列为后续项。**注意：卸载能力本身在范围内（R4），被推迟的只是"安装向导形态"。**
